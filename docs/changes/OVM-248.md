# OVM-248 — admission программных решений

Новый submit проверяет квоты пользователя и всего сервиса в той же транзакции,
что сохраняет submission/outbox. Все replicas сериализуют admission через
PostgreSQL advisory transaction lock `7480248`; отдельный SELECT после ожидания
видит свежие committed rows. Lock берётся до task row lock. Process mutex и
дублирующие счётчики не используются. Цена — последовательный короткий admission.

Считаются queued обоих режимов (ожидание, исполнение, retry). Завершение любым
terminal verdict освобождает слот; retry существующего решения остаётся в слоте.
Повтор ключа проверяется под lock до квоты: прежний результат возвращается даже
при полной очереди. Ошибка outbox откатывает submission и не расходует слот.

Конфигурация всех replicas должна совпадать:

- `CODE_ADMISSION_MAX_PER_USER`: 3, допустимо 1–100.
- `CODE_ADMISSION_MAX_TOTAL`: 1000, допустимо 1–100000.
- `CODE_ADMISSION_RETRY_SECONDS`: 15, допустимо 1–3600.

Отказ: HTTP 429, `code=RATE_LIMITED`, `retry_after_seconds` и `Retry-After`.
Пауза — рекомендация, не обещание доступности; счётчики/чужие ID не раскрываются.
Gateway продолжает читать code/message; отдельный UI таймер не входит в задачу.

Миграция `202611160002_submission_admission.sql` добавляет partial index queued
по user_id. Применяется на остановленных старых writers: смешанный rollout не
гарантирует лимиты. Понижение квоты не отменяет уже принятые решения. Для большого
backlog миграция обычного индекса требует отдельного окна (не CONCURRENTLY).

Проверки: PostgreSQL 17, 24 concurrent requests к разным задачам/пользователям,
12 одновременных повторов ключа, terminal release, rollback outbox; unit/race,
config bounds, HTTP 429 headers, lint/vet/build. Общий live gateway/gojudge стек
не запускался; очередь изменяется только внутри tasks.
