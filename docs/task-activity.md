# Журнал публикаций задач для Feed

Durable-источник событий публикации для пересборки ленты. Дополняет топик
`task.activity.v1`: Kafka остаётся live-путём, журнал переживает её retention
и очистку outbox.

## Источник

Записи создаёт триггер `task_activity_change` на `UPDATE OF status, deleted_at`
таблицы `tasks`, то есть в той же транзакции, что и смена статуса. Поэтому
публикация и запись в журнал атомарны, а отдельный код в usecase не нужен.

Порядок задаёт `task_activity_clock`: триггер блокирует строку часов и
увеличивает `revision`, поэтому номера идут в порядке коммитов. Читатель
берёт watermark из часов и не пропускает ещё не подтверждённые записи.

Типы записей:

- `task.published` — карточка появляется; есть версия, заголовок, тема, тип и
  сложность на момент публикации;
- `task.unpublished` — задача ушла из `published` (архив, возврат в черновик)
  или была удалена; карточка должна исчезнуть.

Данные задачи ограничены публичными полями. Условия, hidden tests, варианты
ответов и приватные поля в журнал не попадают.

Если на момент применения миграции уже были опубликованные задачи, миграция
добавляет для них записи `task.published`; `occurred_at` в этом случае равен
времени миграции, потому что точное время публикации не сохранялось.

## Эндпоинт

`GET /v1/internal/task-activity/changes` — только для внутренних сервисов.
Авторизация: `Authorization: Bearer $TASKS_ACTIVITY_TOKEN` (32–512 печатных
ASCII без пробелов). Без токена маршрут не регистрируется, ответы не кэшируются
(`Cache-Control: no-store`).

Параметры:

| Параметр | Значение |
| --- | --- |
| `watermark` | верхняя граница ревизий; без него фиксируется текущее значение часов |
| `after` | курсор: отдаются записи с `revision > after` |
| `limit` | размер страницы, 1–100, по умолчанию 50 |

Ответ:

```json
{
  "watermark": 42,
  "through": 40,
  "more": true,
  "changes": [
    {
      "revision": 40,
      "event_id": "6f1c1f9e-0f4b-4d0b-9f63-4f6b0b8a2f1e",
      "event_type": "task.published",
      "occurred_at": "2026-11-24T15:00:00Z",
      "task_id": "0a5f5f44-1f6f-4c5e-9d0a-6f5f9a1c2b3d",
      "task_version_id": "c1a2b3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d",
      "title": "Two pointers",
      "topic_id": "1b2c3d4e-5f60-4a71-8b92-0c1d2e3f4a5b",
      "task_type": "programming",
      "difficulty": "easy"
    }
  ]
}
```

`watermark` — граница текущей страницы, `through` — последняя отданная ревизия,
`more` — есть ли ещё записи до `watermark`. Следующая страница запрашивается
с `after=through` и тем же `watermark`. Повтор того же запроса с тем же
watermark и `after` возвращает тот же результат: новые публикации в уже
закреплённую страницу не попадают.

У `task.unpublished` заполнены `task_id`, `task_version_id` и `occurred_at`;
`title`, `topic_id`, `task_type` и `difficulty` могут отсутствовать.

## Ошибки

- `400` — некорректные `watermark`, `after` или `limit`, неизвестный или
  повторяющийся параметр;
- `403` — нет или неверный service token;
- `503` — журнал временно недоступен.

## Хранение

Записи не удаляются автоматически: retention журнала — отдельное решение
оператора. Одна запись занимает только идентификаторы и публичные метаданные,
поэтому рост ограничен числом публикаций и снятий с публикации.
